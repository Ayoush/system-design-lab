# FlashSale — HLD v0

## What changed from the previous version

Nothing — this is the starting point. No prior version exists. v0 is the
naive, deliberately un-scaled baseline every later version gets measured
against.

## Diagram

```
                    ┌─────────────┐
   client  ───────► │  api (1x)   │
                    └──────┬──────┘
                           │
                           ▼
                    ┌─────────────┐
                    │  postgres   │
                    │   (1x)      │
                    └─────────────┘
```

One API process. One Postgres instance. Nothing else — no load balancer,
no cache, no queue, no replica, no connection pooler. The API talks
directly to Postgres over a single, untuned connection pool.

## Why this component, why now

Not applicable at v0 — there's no prior failure forcing this shape. v0
exists to BE the failure. Every component added from v1 onward is a
response to something v0 (or a later version) is measured breaking under.

## What this does NOT solve

v0 has 8 deliberate bugs planted on purpose, listed in full in
`../../README.md`. Restated here as "what this architecture does not
solve," since that's exactly what they are:

1. **Oversell race** — inventory is read, checked, then written as three
   separate steps, not one atomic operation. Concurrent checkouts can both
   read the same inventory count before either writes, both proceed, and
   inventory goes negative.
2. **No index on `orders.product_id`** — `GET /products/:id/orders` forces
   a sequential scan that gets slower as the orders table grows.
3. **Unbounded pagination** — that same endpoint returns every matching
   row, no `LIMIT`, no cursor.
4. **Fully synchronous checkout** — validate → create order → charge →
   send email → record analytics → respond, all inline, all blocking the
   client on every step including ones that don't need to.
5. **No timeouts** on any outbound call — a slow dependency hangs the
   request indefinitely instead of failing fast.
6. **No idempotency enforcement** — a retried or duplicated request can
   create a second order for the same intent.
7. **Untuned connection pool** — default `pg` pool settings, no explicit
   sizing, no acquire timeout.
8. **No cache, no queue, no retry policy, no circuit breaker** — every
   request pays the full cost of every dependency, every time, with no
   isolation when one dependency degrades.

Each of these is a future experiment (`ROADMAP.md` §10) and a future ADR,
not a bug to pre-emptively fix. The point of v0 is watching each one fail
under measured load before knowing, from evidence, what actually fixes it.

## SLO at this version

None. v0 deliberately has no SLO — there's nothing yet worth defending.
The first real SLO gets set at v1, once the naive failures above have
been observed and the system is no longer this fragile by accident.

The one thing worth tracking even at v0, informally: **inventory must
never go negative.** It will. That's the point — EXP-003 exists to prove
it, on the record, before anything gets fixed.
